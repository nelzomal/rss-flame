# 「RSS」有一半不是 RSS，是套了 XML 外壳的抓取

👉 **[打开火焰图](https://nelzomal.github.io/rss-flame/)**

把 [ifeed.cc/discover](https://www.ifeed.cc/discover) 目录里的 **932 个 RSS 订阅源**全部抓了一遍，
按「这段 XML 究竟是怎么生产出来的」分组画成火焰图。条形宽度是订阅数之和，颜色是实测的抓取结果，
可以从目录一路下钻到单个订阅源，看到它的传输格式、条目数、正文长度、是否支持条件请求。

## 结论

只有一半的「RSS」是真 RSS。另一半是第三方抓取网页或封闭平台后再吐出 XML —— 这个区别在任何阅读器界面上都看不见，
而所有的失效都发生在那一半里。

| 生产方式 | 订阅源数 | 占源数 | 订阅数 | 30 天内存活 |
|---|---:|---:|---:|---:|
| 商业抓取 SaaS | 55 | 5.9% | 105 | **88.6%** |
| 平台原生接口 | 27 | 2.9% | 27 | **81.5%** |
| 托管博客 / newsletter | 28 | 3.0% | 44 | 50.0% |
| 站点自建 feed | 488 | 52.4% | 1327 | 65.9% |
| 公共 RSSHub 实例 | 69 | 7.4% | 304 | 73.4% |
| 播客托管 | 18 | 1.9% | 38 | 50.0% |
| FeedBurner 中转（Google） | 53 | 5.7% | 119 | 47.9% |
| Nitter / xcancel 中转（X） | 194 | 20.8% | 199 | **0.0%** |

从 932 个目录条目，到真正还能读的东西：

```
932  目录条目
684  返回 HTTP 200 ............................ 73.4%
657  …并且能解析成 XML ......................... 70.5%
641  …并且条目带日期 ........................... 68.8%
441  …并且 30 天内更新过 ....................... 47.3%
```

## 最坏的失效方式不是 404

`rss.xcancel.com` 一个主机就占了目录的 20.8%（194 个源），而且 **0% 可用**。
它不是打不开 —— 它稳稳返回一份格式完全合法的 RSS 2.0，里面只有一条：

```xml
<title>RSS reader not yet whitelisted!</title>
<description>Please send an email rss [AT] xcancel [DOT] com with this ID
             to get your RSS feed reader whitelisted: 9db973f9…</description>
<pubDate>Mon, 01 January 1971 00:00:00 GMT</pubDate>
```

后果在 ifeed 自己的数据库里已经能看到：这 194 条记录的**标题字段全部变成了
「RSS reader not yet whitelisted!」** —— 阅读器照常解析、照常入库，把哨兵报文当成正文，
把原来的账号名覆盖掉了。一个中转方改一次策略，目录里五分之一的源就被静默污染，没有任何一层会报错。

## 其它实测数字

- **传输格式**：RSS 2.0 占 82.3%，Atom 1.0 占 16.7%，RSS 1.0/RDF 占 0.6%，**JSON Feed 0 个**
- **正文完整度**：只有 35.6% 的源发全文（`<content:encoded>`），单条正文长度中位数 **594 字符**；
  22.3% 只有标题或干脆是空的
- **轮询成本**：25.6% 的源既不给 `ETag` 也不给 `Last-Modified`，条件请求无从谈起；
  完整轮询 657 个源一遍要传 **175 MB**
- **封闭平台**：小红书、抖音 / TikTok、B 站、Instagram 在目录里 **0 个**，直接探测其
  `/rss` 路径也全是 HTML 或 404；X 有 198 个条目，活着 4 个；播客 34 个，活着 34 个

## 怎么复现

```bash
bash scripts/run.sh        # 约 2 分钟，绝大部分时间在等 932 个远端订阅源
```

| 步骤 | 产出 | 做什么 |
|---|---|---|
| `1_fetch_catalog.py` | `data/feeds.json` | 翻页拉全量目录（`/api/discovery/feeds` 未鉴权） |
| `2_probe.py` | `data/probe.json` | 40 并发抓每一个源，记录 HTTP 状态和最新条目日期 |
| `3_formats.py` | `data/formats.json` | 对返回 200 的重抓一遍，解析格式 / 条目数 / 正文长度 / 缓存头 |
| `4_build.py` | `data/flame_data.json` | 归类到 8 种生产方式，建 目录→方式→主机→源 四层树 |
| `5_render.py` | `index.html` | 把数据内联进单文件页面 |

`scripts/analysis/` 是 README 里各个数字的出处（漏斗、格式分布、封闭平台探测、RSSHub 复查）。
`scripts/test_render.py` 用 headless Chrome 驱动下钻 / 搜索 / 切换口径，验证页面交互没坏。

`data/` 不入库：它是某一时刻活体网络的快照，重跑必然和 `index.html` 里那一份不同。
**这种差异本身就是结论**——比如相隔 90 分钟的两次探测里，「平台原生接口」的存活率从 81.5% 掉到约 30%，
只因为 YouTube 和 Reddit 对并发探测限了流。当前页面用的是 2026-08-18 03:07 UTC 那一次。

## 数据怎么来的

`ifeed.cc` 的 `/api/discovery/*` 接口未鉴权，翻页取全量目录，再逐个真实抓取解析。
探测时间 2026-08-18。`index.html` 是单文件、零外部请求，数据内联在页面里。
